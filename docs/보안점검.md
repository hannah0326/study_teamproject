# 배포 전 보안 점검

- 대상: 커밋 `ab201fe` 뒤의 작업 폴더 코드(5단계 작업 중).
- 스택: Streamlit + Streamlit Community Cloud + Supabase(Postgres), 로그인은 학번과 비밀번호(bcrypt 해시).
- 방법: 15개 항목을 지금 코드 기준으로 진단함. 진단만 하고, 위험이 크고 고치기 쉬운 것만 고침(아래 "고친 것").
- 상태: ☑ 구현 / △ 부분 / × 없음 / − 해당없음. 위험도: High / Med / Low.

| 항목 | 상태 | 위험도 | 근거와 수정 방향 |
|---|---|---|---|
| 01. CORS | − | Low | 앱이 따로 여는 API가 없음. Streamlit 서버 기본 설정을 그대로 씀(`.streamlit` 설정 파일 없음). |
| 02. CSRF | ☑ | Low | Streamlit 기본값(XSRF 보호 켜짐)을 바꾸지 않음. |
| 03. XSS + CSP | △ | Low | `unsafe_allow_html` 같은 HTML 그대로 그리기를 쓰지 않음. 명단 이름은 Streamlit 이 글자로 그림. 오픈라우터 문구와 모델 답은 `st.text` 로 마크다운 없이 보임. CSP 등 헤더는 배포 플랫폼이 정함. |
| 04. SSRF | − | Low | 바깥 요청은 고정된 오픈라우터 주소 하나뿐이고, 사용자가 주소를 넣을 곳이 없음. |
| 05. AuthN / AuthZ | △ | Med | 비밀번호는 bcrypt 해시로 비교하고, 학번이 없을 때도 같은 시간이 걸리게 가짜 해시와 비교함. 관리자 기능은 서비스에서 매번 관리자인지 확인함. 학생 비밀번호가 모두 `1234` 인 것은 과제 명세가 정한 것이라 바꾸지 않음(학번을 알면 그 학생으로 로그인 가능). |
| 06. RBAC · 테넌트 | ☑ | Low | 역할은 관리자와 학생 둘이고 서버 쪽에서 나눔. 학생 화면에는 관리자 요소를 그리지 않음. 테넌트는 하나. |
| 07. 최소권한 | × | Med | 앱이 DB에 표 주인(`postgres`, RLS 건너뜀 권한 있음)으로 접속함. 필요한 권한만 가진 계정을 따로 두는 것이 바람직하나, 과제 범위에서는 하지 않음. 대신 Supabase 공개 API 쪽은 RLS 로 막음(아래 "고친 것"). |
| 08. Input + SQLi | ☑ | Low | 모든 질의는 `%s` 매개변수로 값을 넘김. f-문자열은 고정된 하위 질의 상수만 끼움. 명단 CSV 는 열 수·역할 이름·학번 중복을 검사하고 팀 수는 1~10 만 받음. |
| 09. Rate Limit | × | Med | 로그인 시도 횟수 제한이 없음. 관리자 비밀번호를 여러 번 넣어 볼 수 있음. 수정 방향: 학번별 실패 횟수를 세어 잠시 막기. 다만 채점 프로그램이 같은 학번으로 여러 번 로그인하므로 잘못 막으면 채점이 멈출 수 있어, 이번에는 고치지 않고 관리자 비밀번호를 길고 추측하기 어렵게 정하는 것으로 대신함. 오픈라우터 호출은 관리자만 할 수 있고 한 번에 최대 3번. |
| 10. 쿠키 · 세션 | △ | Low | 로그인 상태는 Streamlit 접속별 서버 쪽 상태에만 둠(쿠키를 직접 쓰지 않음). 새로 고치면 로그아웃됨. 명단을 다시 올려 계정이 없어지면 자동으로 로그아웃시킴. |
| 11. Secret · Rotation | △ | Low | 키·DB 주소·관리자 비밀번호는 `.env`(git 무시)와 Streamlit Secrets 에만 둠. 화면·로그·오류에 출력하지 않음(시험으로 확인). 커밋 기록 전체에 `.env` 의 값과 키 모양이 없음을 확인함. 교체 절차는 따로 없음(채점 기간에는 관리자 비밀번호를 바꾸지 않음). |
| 12. HTTPS · 보안헤더 | △ | Low | 배포 플랫폼이 HTTPS 로 서비스함. 헤더는 플랫폼이 정하며 앱에서 바꾸지 않음. |
| 13. Audit Log | △ | Low | AI 호출은 `tf_ai_logs` 에 시작 시각·모델·결과·이유를 남김. 지원과 결정 시각은 `tf_applications` 에 남음. 로그인과 관리자 동작 기록은 없음. |
| 14. 에러 노출 | ☑ | Low | 예기치 못한 오류는 화면에 일반 문구만 보이고, 서버 로그에는 오류 종류만 남김(시험으로 확인). |
| 15. 의존성 취약점 | ☑ | Low | `requirements.txt` 에 버전을 고정함. 2026-10-31 `pip-audit -r requirements.txt` 결과 "No known vulnerabilities found". |

## 고친 것
- **Supabase RLS:** 점검 전 `tf_` 표 8개 모두 RLS 가 꺼져 있었음(2026-10-31 DB 조회로 확인). 꺼져 있으면 Supabase 의 공개 데이터 API 로 비밀번호 해시가 든 `tf_students` 등을 읽을 수 있는 위험이 있음. `schema.sql` 에서 모든 `tf_` 표의 RLS 를 켬. 앱은 표 주인 계정으로 접속해 RLS 의 영향을 받지 않음(DB 시험으로 확인).
- **AI 요청의 예시 학번:** 응답 형식 예시에 연습용 시나리오의 학번을 쓰고 있었음. 형식만 보이는 가짜 번호로 바꿈(자동 점검 시험 `test_no_scenario_names_in_app_code` 가 찾아냄).

## 자동 점검 시험
`tests/test_hygiene.py`: `.env` 무시, 저장소 파일에 비밀 값·키 모양·비밀번호가 든 DB 주소가 없음, `openrouter/free` 를 쓰지 않음, 표 이름 `tf_`, 앱 코드에 연습용 이름·학번이 없음, PRD 5.2절의 key 가 모두 코드에 있음, 모든 `tf_` 표에 RLS 가 켜져 있음(DB).
