## 내 앱에서 발견한 문제
두 건 모두 3단계를 직접 확인하다 발견함. 발견 당시의 코드는 이 기록을 담은 3단계 커밋이고, 고친 커밋의 해시는 고친 뒤에 적음.

- 2026-10-26, 쉬움 2단계(학생1 팀1 지원 → 학생4 팀1 지원 → 학생1 찬성): 내 지원이 다른 팀원의 표로 나중에 승인돼도, 지원한 학생 화면의 `result` 가 지원 직후의 `대기` 로 남음.
  - 화면: 학생1 창은 찬성 직후 `승인`(01:23:59 갱신, `img/7항_쉬움2단계_학생1_찬성직후_승인.png`). 학생4 창은 승인된 뒤에도 `대기` 와 "내 지원: 팀1 — 승인" 이 함께 보임(01:24:06 갱신, `img/7항_쉬움2단계_학생4_승인됐는데_대기로남음.png`).
  - DB 확인: 학생4(2026104)의 지원은 01:23:53 에 접수되고 01:23:56 에 학생1의 찬성 한 표로 승인됨.
  - 판단: `result` 는 "동작한 사람의 화면에 그 동작 직후의 상태" 라는 명세는 지키지만, 쓰는 사람에게는 한 화면의 상태가 서로 어긋나 보임. 원인은 `result` 를 다음 동작까지 유지하기로 하면서 다른 사람의 동작으로 내 상태가 바뀌는 경우를 설계에서 따지지 않은 것.
- 2026-10-26, 쉬움 명단을 다시 올린 뒤 1단계(학생1이 팀1에 지원): 명단을 다시 올리기 전에 로그인해 둔 학생의 지원이 `막힘: 처리 중 오류가 발생함. 잠시 뒤 다시 시도하세요` 로 실패함.
  - 순서(직접 해 본 사용자의 확인): 학생1 로그인 → 관리자가 같은 쉬움 명단을 다시 올림(01:39) → 학생1 창이 5초 갱신 뒤 팀이 모두 0/4, "아직 팀이 없음" 으로 바뀜(01:39:19) → 학생1이 팀1에 지원하자 오류(01:39:34). 처음 발견은 01:30 이고, 화면을 남기려고 같은 순서로 01:39 에 다시 함.
  - 화면: `img/7항_명단재업로드_1_관리자_같은명단다시올림.png`, `img/7항_명단재업로드_2_학생1_갱신뒤_팀없음.png`, `img/7항_명단재업로드_3_학생1_팀1지원_오류.png`.
  - DB 확인(직접 근거): 01:39:34 의 지원 뒤 조회했을 때 지원 기록이 0건(막힘 판정이 아니라 처리 중 실패).
  - DB 확인(원인을 뒷받침하는 간접 근거): 학생1(2026101)의 계정 번호가 처음 발견 직후 조회에서 212, 다시 해 본 뒤 조회에서 284. 그 사이 명단을 여러 번 다시 올렸고, 올릴 때마다 학생 계정을 지우고 새 번호로 다시 만든다는 것을 보여 줌. 01:39 직전에 학생1 창이 가진 번호 자체는 확인하지 못함.
  - 원인: 로그인한 창이 로그인할 때 받은 계정 번호를 계속 쓰는데, 명단을 다시 올리면 그 번호의 계정이 없어짐. 화면은 새 상태로 바뀌어 멀쩡해 보임.
  - 함께 본 것: 앱은 예기치 못한 오류의 종류를 서버 로그에 적게 되어 있으나, 이때 로그에 아무것도 남지 않아 오류 종류는 확인하지 못함.
