# PRD: 팀 프로젝트 팀 편성 웹 앱

> 표기: **(제 판단)** 은 요구에 적혀 있지 않아 작성 단계에서 정한 사항임. 구현 전에 확인하고, 바꾸려면 이 문서를 먼저 고침.

## 1. 개요

### 1.1 한 줄 요약
학생들이 팀 프로젝트를 위한 팀을 스스로 편성하는 웹 앱임. 학생은 팀에 지원하고 팀원은 찬반 투표로 받아들이며, 모집을 마감한 뒤 팀이 없는 학생은 AI가 배정을 돕고 앱이 AI의 답을 규칙으로 검사함.

### 1.2 배경과 목적
- 채점은 자동 채점 프로그램이 배포한 앱을 직접 조작하며 진행함. 가상 학생마다 브라우저를 따로 열어 시나리오의 단계를 차례로 실행하고, 단계마다 결과 안내의 첫 단어가 기대 결과와 같은지 확인함.
- 따라서 이 앱의 1차 목표는 **공개하지 않은 시나리오 3개(쉬움, 중간, 어려움)를 모든 단계에서 기대 결과대로 통과**하는 것임.
- 2차 목표는 어려운 해결을 모두 택해 30점 만점을 받는 것임(3.2절).

### 1.3 마감과 일정
- 제출 마감: 2026-11-02(월) 23:59. 마감 뒤 커밋은 감점.
- 채점 기간: 2026-11-03(화)~11-04(수). 이 기간에 DB가 일시정지되어 있거나 관리자 비밀번호가 바뀌면 시나리오 점수가 0점.
- 저장소는 마감 뒤 11-03 09:00까지 공개로 바꿈.

### 1.4 목표, 비목표, 반목표
**목표**
- 연습용 시나리오 3개의 모든 단계가 기대 결과와 일치함.
- 학생 수 8~16명, 팀 수 3~4개, 이름·역할·지원과 투표 순서가 다른 시나리오에서도 규칙대로 동작함.
- AI가 실패해도 확정한 팀 구성은 항상 규칙을 지킴.

**비목표**
- 구글 로그인(`st.login`) 등 외부 인증. 학번과 비밀번호만 씀.
- 학생의 비밀번호 변경, 역할 변경, 팀 이름 변경, 투표 취소나 변경.
- 관리자가 배정안을 손으로 고치는 기능.
- 모바일 전용 화면 최적화(깨지지 않는 정도면 충분함).

**반목표(기술적으로 동작해도 실패로 보는 것)**
- 연습용 시나리오의 학생 이름이나 순서를 보고 결과를 미리 정해 둔 코드.
- 키, DB 주소, 관리자 비밀번호가 코드, 커밋 기록, 화면에 노출되는 것.
- 화면 요소의 key가 표와 다른 것(채점 프로그램이 멈춤).
- 확정한 팀 구성이 규칙을 어기는 것.

## 2. 사용자와 규칙

### 2.1 사용자
| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생 | 학번 + 비밀번호(모두 `1234`) | 팀 목록, 팀원, 팀원의 주 역할과 보조 역할 보기. 팀에 지원하기. 내 팀에 들어온 지원에 찬성/거부 |
| 관리자 | 학번 `admin` + `ADMIN_PASSWORD` | 명단 CSV와 팀 수로 처음 상태 만들기, 모집 마감, AI 배정 실행, 배정안 확정 |

- 학생은 명단 CSV의 가상 학생임. 실제 사람의 이름과 학번은 어디에도 쓰지 않음.
- 관리자 계정은 앱이 시작할 때 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신함. 명단을 다시 올려도 관리자 계정은 남김.

### 2.2 역할
6개: 기획자(PL), 웹 프로그래머(WP), 프론트엔드 디자이너(FD), 테스터(TT), 보고서 작성자(RW), 발표자(PT). 학생마다 주 역할 1개, 보조 역할 0~2개. 학생이 바꾸지 못함.

### 2.3 팀 규칙
| 규칙 | 내용 |
|---|---|
| 팀 수 | 관리자가 명단을 올릴 때 넣은 수만큼 팀을 만듦(팀1, 팀2, …) |
| 인원 | 확정한 팀은 모두 2~4명. 빈 팀 없음 |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 됨 |
| 필수 포함 역할 | 확정한 팀마다 기획자 역할과 웹 프로그래머 역할을 **서로 다른 사람**이 1명씩 맡을 수 있어야 함. 주 역할이나 보조 역할로 맡음 |

주 역할은 팀 안의 중복을 따지는 기준이고, 보조 역할은 필수 포함 역할을 맡을 수 있는지 따질 때만 씀.

### 2.4 판정 함수 정의
구현에서 하나의 순수 함수 모듈(`rules`)에 두고 화면과 DB가 모두 이것을 부름.

- `can(학생, 역할)` = 학생의 주 역할 == 역할 **또는** 역할 ∈ 학생의 보조 역할.
- `커버(팀원 집합)` = 서로 다른 두 사람 a, b가 있어 `can(a, PL)` 이고 `can(b, WP)` 이면 2. 아니면 PL 또는 WP를 맡을 수 있는 사람이 한 명이라도 있으면 1. 없으면 0. 한 학생이 둘 다 할 수 있어도 1명으로만 셈.
- `미충족 수(팀원 집합)` = 2 − `커버`.
- `주 역할 중복(팀원 집합)` = 주 역할 값이 겹치는 두 학생이 있음.
- **지원 가능 검사(팀 T, 지원자 A)** — 아래 순서로 검사해 처음 걸린 이유를 돌려줌(이유 문구는 5.4절).
  1. 모집이 마감됨
  2. A가 이미 팀이 있음
  3. A에게 결과를 기다리는 지원이 있음
  4. T가 4명임
  5. T의 팀원과 A의 주 역할이 같음
  6. **필수 포함 역할 자리 부족**: `남는 자리 = 4 − (|T| + 1)` 이 `미충족 수(T의 팀원 ∪ {A})` 보다 작음
- **승인 직전 재검사(팀 T의 현재 팀원, 지원자 A)** — 정원(4명 이하), 주 역할 중복, 필수 포함 역할 자리를 **그 시점의 팀원 기준으로** 다시 검사함(지원 시점 결과를 재사용하지 않음). 하나라도 어기면 그 지원은 거절.

필수 포함 역할 자리 예(구현의 단위 테스트로 그대로 옮김)
- 주 역할이 기획자이고 보조 역할이 웹 프로그래머인 학생 혼자 있는 팀은 필수 2개 가운데 1개만 채운 것임(`커버` = 1).
- 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면 남는 자리 1개로 미충족 2개를 채울 수 없으므로 막음.

## 4. 기술 구성 (제 판단)

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어, 화면 | Python 3.12, Streamlit | 필수. 배포는 Streamlit Community Cloud |
| DB | Supabase(Postgres), 기존 프로젝트 재사용. 연결은 Session pooler(5432) | 이미 동작을 확인함. 테이블 이름은 모두 `tf_` 로 시작 |
| DB 접근 | `psycopg`(v3) + `psycopg_pool` 의 연결 풀 | 연결은 한 번만 만들어 재사용(풀을 `st.cache_resource` 로 캐시). 풀 크기 2~4 |
| 비밀번호 | `bcrypt`, 해시만 저장. 비용(rounds)은 10 | 명단 16명을 올릴 때 대기 시간이 길지 않게 함 |
| AI 호출 | 오픈라우터 `chat/completions` (`requests`), 별도 스레드 + 전체 시간 제한 | 요청 함수의 시간 제한 값은 응답 시작까지만 재는 경우가 있어 사용하지 않음 |
| 시각 표시 | `zoneinfo.ZoneInfo("Asia/Seoul")` 로 변환 (`tzdata` 의존성 포함) | 배포 서버의 시각은 UTC |
| 설정 읽기 | 환경 변수 → 없으면 `st.secrets`. 로컬은 `.env` | `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` |
| 테스트 | `pytest`, Streamlit `AppTest` | AI는 가짜 응답으로 대체해 하루 호출 한도를 쓰지 않음 |

## 5. 화면과 동작

### 5.1 공통
- 로그인하지 않았으면 로그인 화면만 보임. 로그인한 뒤에는 학생 화면 또는 관리자 화면.
- 로그인: 학번과 비밀번호가 DB와 모두 맞아야 함. 틀리면 안내만 보여 줌(어느 쪽이 틀렸는지는 알리지 않음).
- 관리자 기능(명단 올리기, 마감, 배정, 확정)은 서버 쪽에서 로그인한 사용자가 관리자인지 **매번** 확인함. 학생 화면에서는 이 요소를 아예 그리지 않음.
- 화면에 시각을 보일 때는 한국 시각.
- 예기치 못한 오류가 나도 화면에 `DATABASE_URL`, 키, DB 비밀번호를 출력하지 않음(오류 문구는 일반 문구로 바꿈).

### 5.2 화면 요소 key 표 (표와 정확히 같아야 함)
| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 로그인 단추 | `st.button` 또는 `st.form_submit_button` | `login_submit` |
| 로그인한 사람 표시(이름이 보임) | `st.container` | `whoami` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시(팀원 이름이 보임) | `st.container` | `team_1`, `team_2`, … |
| 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 지원에 찬성하는 단추 | `st.button` | `vote_yes_{지원자 학번}` |
| 지원에 거부하는 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 명단으로 처음 상태 만들기 | `st.button` | `admin_start` |
| 모집 마감 단추 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시(이름이 보임) | `st.container` | `unassigned` |
| AI 배정 단추 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 단추 | `st.button` | `admin_confirm` |

- 새로 고침 단추(`refresh`)는 만들지 않음(자동 갱신을 택함). 채점 프로그램은 "동작하기 전에 이 단추가 있으면 먼저 누름"이므로 없어도 동작함.
- key는 영문, 숫자, 밑줄만 씀. `st.container(key=...)` 를 지원하는 Streamlit 버전을 `requirements.txt` 에 고정하고 구현 1단계에서 확인함.
- 화면에 보이는 글자는 자유. 단, 단추를 누른 결과 안내는 `result` 안에 보임.

### 5.3 결과 안내(`result`)의 첫 단어
`result` 는 "승인", "대기", "거절", "막힘" 가운데 하나로 시작함. 예: `막힘: 같은 주 역할의 팀원이 있음`.

| 동작 | 결과 안내 |
|---|---|
| 지원 단추 → 빈 팀 | `승인: …` 바로 승인 |
| 지원 단추 → 팀원이 있는 팀 | `대기: …` 팀원 전원의 투표를 기다림 |
| 지원 단추 → 규칙에 걸림 | `막힘: <이유>` (접수하지 않음. DB에 기록하지 않아도 됨) |
| 찬성 → 아직 투표하지 않은 팀원이 있음 | `대기: …` |
| 찬성 → 모든 팀원이 찬성하고 재검사 통과 | `승인: …` |
| 찬성 → 모든 팀원이 찬성했지만 재검사에서 규칙을 어김 | `거절: 승인 직전 검사에서 <이유>` |
| 거부 | `거절: …` (다른 팀원의 투표를 기다리지 않음) |
| 관리자 단추 성공 | `승인: …` (예: `승인: 모집을 마감함`) |
| 관리자 단추 실패 | `막힘: <이유>` |

- 찬성/거부 단추의 결과 안내는 그 지원의 **지금 상태**(승인, 대기, 거절)를 보여 줌.
- 한 단계에 동작이 여럿이면 동작마다 `result` 를 확인하므로, 같은 `result` 에 마지막 동작의 결과가 보임.
- 막힘 이유 문구: `팀이 꽉 참`, `같은 주 역할의 팀원이 있음`, `이미 팀이 있음`, `결과를 기다리는 지원이 있음`, `모집이 마감됨`, `필수 포함 역할을 맡을 학생의 자리가 모자람`.

### 5.4 학생 화면
- 상단 `whoami`: 로그인한 학생의 이름.
- 팀마다 `team_N` 컨테이너: 팀 이름, 인원(n/4), 팀원의 이름과 주 역할·보조 역할. 내가 속한 팀에는 "내 팀" 표시. 팀이 없으면 "아직 팀이 없음" 표시(채점하지 않음).
- 지원 단추 `apply_N`:
  - **숨기거나 비활성화**: 이미 팀에 속함, 결과를 기다리는 지원이 있음, 모집이 마감됨. 채점 프로그램은 단추가 없거나 비활성이면 "막힘"으로 봄.
  - 그 밖(팀이 꽉 참, 같은 주 역할 등)은 단추를 **보이게 두고** 누르면 `막힘: 이유`. **(제 판단)**
- 내 팀에 대기 중인 지원이 있으면 지원자 이름, 역할, 현재 투표 현황과 함께 `vote_yes_{학번}`, `vote_no_{학번}` 단추. 이미 투표한 지원은 단추를 숨기거나 비활성화하고 `내 투표: 찬성`처럼 보여 줌.
- 내 지원의 상태(대기, 승인, 거절 이유)도 보여 줌.
- `team_N`, 지원 목록, `result` 는 한 개의 `st.fragment(run_every=5)` 안에 두어 다른 사람의 변경이 5초 이내에 나타남. 마지막 `result` 는 다음 동작까지 유지함 **(제 판단)**.

### 5.5 관리자 화면
1. **명단 올리기**: `admin_roster_file`(CSV), `admin_team_count`(정수, 1~10), `admin_start`. 누르면 지원, 투표, 팀원, 마감 표시를 모두 지우고 명단의 학생과 팀 수만큼의 빈 팀을 만듦. 관리자 계정은 남김.
2. **모집 마감**: `admin_close`. 지원과 투표를 막고, 대기 중인 지원을 거절하고(이유 `모집 마감`), **1명뿐인 팀의 학생을 팀에서 뺌**. 결과는 `unassigned` 로 확인.
3. **AI 배정**: `admin_assign`. 진행 상황과 실패, "규칙을 지키는 배정이 없음" 안내는 모두 `assign_status` 안에 보임.
4. **확정**: `admin_confirm`. 검사를 통과한 배정안만 DB에 저장함.
- 관리자 화면에도 팀 현황(`team_N`)과 `unassigned` 를 보임. 학생 화면과 같은 key 이름을 쓰되 한 화면에 한 번씩만 그림.
- 단추 순서 제약: 명단 올리기 전에는 마감 불가, 마감 전에는 배정 불가, 배정안이 없으면 확정 불가 → `막힘: <이유>`.

### 5.6 명단 CSV
```
student_no,name,main_role,sub_roles
2026001,가나다,기획자,보고서 작성자
2026002,라마바,웹 프로그래머,
2026003,사아자,테스터,기획자;발표자
```
- 인코딩은 UTF-8이며 BOM이 있어도 읽음(`utf-8-sig`). 값 앞뒤 공백은 제거.
- `sub_roles` 는 `;` 로 구분하고 없으면 빈칸. 쉼표가 모자라 열이 3개가 되면 오류.
- 검증 실패는 `admin_start` 의 `result` 에 `막힘: <이유>` 로 알림(이 경우 기존 상태는 바꾸지 않음): 열 이름이 다름, 열 수가 다름, 학번 중복, 역할이 6개 밖의 값, 보조 역할이 3개 이상, 보조 역할에 주 역할과 같은 값, 학번이 `admin`.
- 학생 비밀번호는 모두 `1234`(해시로 저장).

## 6. 지원, 투표, 마감, 배정의 동작

### 6.1 지원
`지원 가능 검사` (2.4절) 통과 시:
- T가 비어 있음 → 즉시 승인(팀원으로 등록).
- 아니면 대기(투표 필요 인원은 투표하는 때의 팀원 전체).

### 6.2 투표
- 투표 자격: 투표하는 때의 T의 팀원이고, 아직 이 지원에 투표하지 않았으며, 지원이 대기 상태일 것. 한 번 투표하면 바꾸지 못함.
- **거부**: 즉시 거절. 다른 팀원의 투표를 기다리지 않음.
- **찬성**: 지금의 팀원 전원이 찬성했는지 확인.
  - 아니면 대기 유지.
  - 맞으면 **같은 트랜잭션 안에서** 승인 직전 재검사. 통과하면 팀원으로 등록하고 승인, 어기면 거절(이유를 `reason` 에 기록).
- 지원 후에 다른 지원자가 먼저 승인되어 팀원이 늘어나면, 그 새 팀원도 기존 대기 지원에 투표해야 함. 그 전에는 대기 중인 지원을 미리 거절하지 않음.
- 처리 순서는 지원 순서가 아니라 투표가 끝난 순서. 팀 단위로 행을 잠가(`SELECT … FOR UPDATE`) 순서대로 처리함.

### 6.3 동시 입력 방어
- `tf_members` 의 `(team_id, slot_no)` 와 `student_id` 유일성 제약이 최종 방어선. 같은 슬롯이나 같은 학생이 두 번 들어오면 DB가 막고, 앱은 그 지원을 거절하고 이유(`먼저 도착한 학생이 자리를 차지함`)를 기록.
- `slot_no` 는 1~4 check.

### 6.4 마감
순서대로: 마감 표시 → 대기 중인 지원을 모두 거절 → 팀원이 1명뿐인 팀에서 그 학생을 뺌 → 팀이 없는 학생 목록 갱신. 이후 지원과 투표는 막힘.

### 6.5 AI 배정
1. 입력: 지금 팀 구성, 팀이 없는 학생과 그 역할(주 역할, 보조 역할), 2.3절 규칙. **이미 팀에 있는 학생은 옮기지 않음.**
2. **먼저 완전탐색으로 가능 여부를 확인함.** 규칙을 지키는 배정이 하나도 없으면 AI를 부르지 않고 `assign_status` 에 `규칙을 지키는 배정이 없음`과 이유(예: `팀3에 웹 프로그래머를 맡을 학생이 없음`)를 보여 주고 끝냄.
3. 가능하면 1차 → 2차 → 3차 모델 순서로 요청. 모델마다:
   - 시작할 때 `assign_status` 에 `1차 모델(이름) 응답을 기다리는 중 … 경과 N초` 를 보임(몇 초마다 갱신).
   - 시작한 때부터 응답을 받을 때까지 **전체 120초**를 재서 넘으면 끊고 다음 모델로.
   - 응답이 비었거나 오류거나 JSON을 읽을 수 없거나 5가지 검사에 실패하면 다음 모델로.
4. 5가지 검사: ① 팀이 없는 학생이 빠짐없이 배정됨 ② 한 학생은 한 팀에만 ③ 모든 팀이 2~4명 ④ 팀 안에서 주 역할 중복 없음 ⑤ 필수 포함 역할 충족.
5. 3차까지 실패하면 앱이 `solver` 로 직접 배정하고 `assign_status` 에 "3차 모델까지 실패하여 앱이 직접 배정함"을 보임. `solver` 는 5가지 검사를 모두 통과하는 배정을 모든 경우를 따져 찾음(가지치기 사용).
6. 검사를 통과한 배정안만 관리자에게 보여 줌(학생의 이름과 역할, 배정된 팀). `admin_confirm` 을 누르면 다시 검사한 뒤 DB에 저장함. 배정안은 DB(`tf_settings`)에도 보관해 화면을 다시 그려도 유지함 **(제 판단)**.
7. 모든 호출은 `tf_ai_logs` 에 기록(차수, 모델, 결과, 소요 시간). 키는 기록하지 않음.
8. 전체 AI 배정은 어떤 경우에도 10분을 넘기지 않음(최대 3×120초 + 직접 배정).

### 6.6 확정과 재조회
확정하면 팀 구성이 DB에 남아, 새 브라우저로 열어도 같은 팀 구성이 보임. 명단을 다시 올리면 모두 초기화.

## 7. 데이터 모델
`schema.sql` 이 아래와 완전히 같아야 하며, 앱이 실제로 쓰는 테이블, 열, 제약과 일치함.

| 테이블 | 열 | 제약 |
|---|---|---|
| `tf_students` | `id`, `student_no`(유일), `name`, `main_role`, `password_hash`, `is_admin` | `main_role` check(6개 역할) |
| `tf_student_sub_roles` | `student_id`, `role` | `role` check, `(student_id, role)` 유일 |
| `tf_teams` | `id`, `name`(유일) | |
| `tf_members` | `team_id`, `slot_no`, `student_id` | PK `(team_id, slot_no)`, `student_id` 유일, `slot_no` check 1~4 |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`, `reason`, `created_at`, `decided_at` | `status` check(대기, 승인, 거절) |
| `tf_votes` | `application_id`, `voter_id`, `vote` | PK `(application_id, voter_id)`, `vote` check(찬성, 거부) |

- 한 학생이 동시에 대기 지원을 두 개 가질 수 없음: 앱 검사와 함께 `tf_applications` 에 `status='대기'` 인 `student_id` 부분 유일 인덱스를 둠 **(제 판단)**.
- 상태 값 표기: 화면, DB 모두 한국어 값(`대기`, `승인`, `거절`, `찬성`, `거부`)을 씀.

## 8. 보안과 운영

- **키 관리**: `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` 는 로컬 `.env`, 배포 앱에서는 Streamlit Secrets에만 둠. 코드, 문서, 커밋 기록에 쓰지 않음. 커밋 전에 `.env` 가 무시되는지 확인함.
- **출력 금지**: 키와 DB 주소를 화면, 로그, 오류 문구에 출력하지 않음. 필요하면 "있음/없음"만 보임.
- **관리자 비밀번호**: 채점 기간 동안 바꾸지 않음. 제출 칸의 값, `.env`, Secrets의 값이 모두 같아야 함.
- **권한**: 학생 계정으로 관리자 기능을 쓸 수 없음(서버 쪽 확인). 비밀번호가 틀리면 로그인되지 않음.
- **연결**: 연결 풀을 한 번만 만들어 재사용. 꺼낼 때 확인 질의를 보내 끊긴 연결이면 풀을 새로 만듦(앱이 잠들었다 깰 때 대비).
- **배포**: Streamlit Community Cloud. 비공개 저장소로 배포한 앱은 "public and searchable" 로 바꾸고, 로그인하지 않은 브라우저(시크릿 창)로 로그인 화면이 보이는지 확인. Branch 칸은 저장소의 기본 브랜치 이름.
- **DB 일시정지 방지**: 마감 날(11/2)에 배포한 앱에서 명단을 올리고 지원과 투표를 해 DB를 씀. 선택 항목은 12.3절.
- **개인정보**: 명단, 코드, 문서, 화면 캡처에 실제 사람의 이름이나 학번을 쓰지 않음. 연습용 가상 명단만 씀.

## 9. 구현 단계와 완료 기준
단계마다 완료 기준을 확인하고, 사람이 직접 화면에서 확인한 뒤 다음 단계로 진행함. 단계가 끝날 때마다 화면 캡처를 `img/` 에 남김.

### 1단계: 규칙 엔진과 솔버
- 만들 것: `rules`, `solver`, `roster`, 연습용 시나리오 3개를 데이터로 담은 테스트.
- 완료 기준
  - 부록 A의 모든 단계가 인메모리 상태에서 기대 결과와 일치(쉬움, 중간, 어려움 모두).
  - 필수 포함 역할 자리 예제(2.4절)가 모두 통과.
  - `solver` 가 부록 A 어려움의 마감 직후 상태에서 5가지 검사를 모두 통과하는 배정을 찾고, 불가능한 입력에서는 "없음"과 사유를 돌려줌.
  - 학생 수 16명, 팀 4개 입력에서 1초 안에 끝남.

### 2단계: DB, 로그인, 명단
- 만들 것: `schema.sql`, 연결 풀, 관리자 계정 생성, bcrypt 로그인, 명단 올리기 서비스.
- 완료 기준
  - `schema.sql` 이 실제 DB와 일치(유일성, check 제약 포함).
  - 학생과 관리자로 로그인이 되고, 비밀번호가 틀리면 로그인되지 않음. `tf_students.password_hash` 에 평문이 없음.
  - 명단을 올리면 상태가 초기화되고 관리자 계정은 남음. BOM이 있는 CSV와 없는 CSV 모두 읽힘. 잘못된 CSV는 `막힘`.

### 3단계: 학생 화면과 서비스
- 만들 것: 지원, 투표, 승인 직전 재검사, 학생 화면, 5초 자동 갱신, key 표의 요소.
- 완료 기준
  - 부록 A의 쉬움, 중간, 어려움 1~마감 전 단계를 실제 화면에서 순서대로 해 보고 `result` 첫 단어가 기대 결과와 일치.
  - 다른 브라우저의 지원과 투표가 5초 안에 화면에 나타남.
  - Streamlit `AppTest` 로 key 표의 모든 요소를 찾을 수 있음.

### 4단계: 마감과 AI 배정
- 만들 것: 마감 처리, `ai`, `assign_flow`, `assign_status`, `admin_confirm`.
- 완료 기준
  - 마감 결과를 `unassigned` 로 확인(대기 지원 거절, 1명 팀 해체).
  - 가짜 AI 응답 시험: 성공, 빈 응답, 404, 429, 120초 초과, JSON 오류, 규칙 위반 응답에서 다음 모델로 넘어가고, 3차까지 실패하면 앱이 직접 배정해 규칙을 지킴.
  - 규칙을 지키는 배정이 없는 입력에서 AI를 부르지 않고 이유를 보여 줌.
  - 확정한 팀 구성이 새 브라우저에서도 남아 있음.
  - 실제 AI는 소수 호출로 시험하고 모델 3개를 확정.

### 5단계: 배포와 마무리
- 만들 것: 배포, 보안 점검, README, 근거 화면, 저장소 압축 파일.
- 완료 기준
  - 배포 주소에서 부록 A의 3개 시나리오를 처음부터 끝까지 통과.
  - 시크릿 창에서 로그인 화면이 보임. Secrets에 키 3개를 넣고 값이 `.env` 와 같음.
  - README 7.1절의 항목 1~7이 모두 있고, 5~7항은 화면이나 커밋 근거가 있음.
  - 저장소와 압축 파일에 `.env` 가 없음.

## 10. 검증 기준

### 10.1 시나리오 통과
연습용 시나리오 3개(부록 A)를 한 단계도 빼지 않고 통과해야 함. 채점용 시나리오는 학생 수 8~16명, 팀 수 3~4개, 이름, 역할, 순서가 다를 수 있으므로 **특정 이름이나 순서에 의존하는 코드를 쓰지 않음**.

### 10.2 시험 종류
- 규칙 단위 테스트(`rules`, `solver`): 경계 값과 부록 A의 모든 단계.
- 서비스 통합 테스트(DB 필요): 지원 → 투표 → 마감 → 확정의 흐름을 개발용 상태에서 실행하고, 끝나면 초기화함 **(제 판단)**.
- 화면 테스트(`AppTest`): key 표의 요소가 모두 존재하고, 숨기거나 비활성화해야 하는 상태에서 단추가 그렇게 보임.
- 가짜 AI 시험: 3.2절의 실패 유형별 분기.
- 직접 확인: 부록 A를 화면에서 위에서부터 해 보며 결과 안내의 첫 단어를 비교하고, 발견한 문제를 README 7항에 적음.

### 10.3 README에 남길 근거 (개발 중에 바로 모음)
- AI 호출 실패 사례 1건 이상과 그 화면(`img/`).
- 개발 보조 도구가 틀린 판단을 한 사례 1건 이상과 알아챈 방법(화면이나 커밋 해시).
- 내 앱에서 발견한 문제점 1건 이상, 발견한 시나리오 단계와 화면.
- 꾸며 낸 화면이나 기록은 쓰지 않음.

## 11. 가정과 제 판단 목록
1. 새로 고침 단추는 만들지 않고 `st.fragment` 자동 갱신만 씀(5.2절).
2. 팀이 꽉 찼거나 주 역할이 같은 경우의 지원 단추는 숨기지 않고 누르면 `막힘`(5.4절).
3. 모델 3개는 임시이며 4단계에서 확정함(4.1절).
4. 풀 크기 2~4, bcrypt 비용 10, `tzdata` 포함(4절).
5. 배정안을 `tf_settings` 에 보관(6.5절), `tf_ai_logs` 추가(7절), 대기 지원 부분 유일 인덱스(7절).
6. 서비스 통합 테스트는 개발용 DB 상태에서 실행하고 끝나면 초기화(10.2절).
7. `st.container` 의 key 지원 버전은 구현 1단계에서 확인해 `requirements.txt` 에 고정(5.2절).

## 12. 열린 질문

### 12.1 새로 고침 단추를 만들지 말지
자동 갱신이 채점 프로그램의 클릭과 겹쳐 실패할 가능성에 대비하려면 `refresh` 단추를 같이 둘 수 있음. 다만 그러면 어려운 해결(1점)을 택했다고 보기 어려울 수 있어 지금은 두지 않기로 함. 구현 3단계의 시험에서 불안정하면 다시 정함.

### 12.2 앱 파일 이름
진입 파일은 `streamlit_app.py` 로 함. 배포할 때 Main file path 칸에 같은 이름을 넣음.

### 12.3 DB 일시정지 방지의 외부 예약 서비스
저장소의 예약 실행(GitHub Actions)에서 하루 한 번 DB에 `select 1` 을 보내는 방식을 후보로 함. 이 방식은 저장소 비밀 값(`DATABASE_URL`)을 따로 등록해야 하고 점수는 0.5점. 5단계에서 다른 항목이 끝난 뒤 도입 여부를 정함. 도입하지 않아도 11/2의 직접 사용과 마감 직전 점검으로 일시정지는 막음.

### 12.4 저장소와 브랜치
저장소는 비공개로 만들고 기본 브랜치에서 단계마다 커밋함. 배포는 기본 브랜치 기준.
