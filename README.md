## 3. 고른 해결 방법

모든 기능에서 어려운 해결을 골랐음(PRD 3.2절과 같음).

| 기능 | 고른 해결 | 어떻게 만들었는지 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every=5)` 로 팀 목록, 지원 목록, 결과 안내를 5초마다 다시 그림. 새로 고침 단추는 두지 않음 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원 단계에서, 지원자가 들어간 뒤 남는 자리가 아직 채우지 못한 필수 포함 역할 수보다 적으면 `막힘: 필수 포함 역할을 맡을 학생의 자리가 모자람` |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 승인 직전에 규칙을 다시 검사함. 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | DB 유일성 제약(`tf_members` 의 `(team_id, slot_no)` 기본 키와 `student_id` 유일)으로 먼저 도착한 학생만 기록. [`schema.sql`](schema.sql) |
| AI 응답이 늦을 때 | 어려운 해결 | 모델마다 요청 시작부터 응답을 다 받을 때까지 전체 120초를 재서 끊고 다음 모델로 넘어감 |
| 3차 모델까지 실패 | 어려운 해결 | 앱이 5가지 검사를 모두 통과하는 배정을 완전탐색(가지치기)으로 찾음 |
| AI 대기 중 화면 | 어려운 해결 | `assign_status` 에 "N차 모델(이름) 응답을 기다리는 중 … 경과 N초" 를 1초마다 갱신해 보여 줌 |
| DB(Supabase)가 일시정지되지 않게 | 어려운 해결 | 외부 예약 서비스(GitHub Actions, [`.github/workflows/db-keepalive.yml`](.github/workflows/db-keepalive.yml))로 매일 한국 시각 오전 9시에 DB 에 `select 1`. [실행 성공 화면](img/3항_DB일시정지방지_2_진단추가뒤_성공.png) |

## 6. 클로드가 잘못된 추론이나 답변을 한 사례

1. **새 파일의 작성 시각을 짐작해 미래 시각을 적음** (1단계, 커밋 `a5f5f94`): 실제 한국 시각은 23시대인데 파일에 23:40, 23:55, 다음 날 00:10 같은 시각을 적음. 2단계를 시작하며 시스템 시각을 다시 구하다 실제보다 늦은 값이 있는 것을 알아챘고, 파일 생성 시각과 대조해 21개 파일을 바로잡음(커밋 `cfcf11f`). 3단계에서 같은 실수가 한 번 더 있었고(시험 파일 2개), 현재 시각과 파일 생성 시각을 대조해 커밋 전에 바로잡음(커밋 `e2fb517` 에 들어감).

## 7. 앱에서 발견한 문제점과 개선 사항

1. **내 지원이 나중에 승인돼도 `result` 가 `대기` 로 남음** — 연습용 쉬움 2단계(학생4 지원 → 학생1 찬성). 학생4 화면에 `대기` 와 "내 지원: 팀1 — 승인" 이 함께 보여 헷갈림. 발견 커밋 `e2fb517`, 고친 커밋 `ad4d3c3`(`result` 는 그대로 두고 "내 지원이 팀1에 승인됨" 안내를 따로 보임, 재현 시험을 먼저 씀).

## 실행 방법(로컬)

1. Python 3.12, `pip install -r requirements.txt`
2. 앱 파일과 같은 폴더에 `.env` 를 만들고 `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD` 를 넣음(형식은 [`.env.example`](.env.example)). 배포한 앱에서는 같은 이름으로 Streamlit Secrets 에 넣음.
3. `streamlit run streamlit_app.py`
4. 시험: `pytest -q`(DB 시험은 `RUN_DB_TESTS=1` 일 때만 실행되며 개발용 DB 의 `tf_` 데이터를 지움)
